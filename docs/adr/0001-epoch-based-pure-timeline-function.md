# Epoch-based pure function for channel scheduling, not a persisted schedule

Status: accepted

We considered materializing each Channel's schedule as a stored sequence of (item, start, end) rows, generated ahead of time and regenerated in the background as the Playlist changes. Instead, a Channel's schedule is computed on demand by a single pure function, `ProgramAt(channel, t) → Airing`, called by both the live streamer and the XMLTV guide writer.

We chose this because it structurally guarantees the stream and the published guide can never disagree about what's airing — there is no second code path or background job that could drift out of sync, which research into Plex's guide behavior flagged as the central risk of this class of app. The cost is that editing a Channel's folder changes what airs, immediately, for the whole cycle — mitigated by scoping each edit to a new immutable **Epoch** (see [CONTEXT.md](../../CONTEXT.md)) rather than rewriting history, so a guide that has already published upcoming listings doesn't retroactively become wrong.

Considered and rejected: a persisted/materialized schedule table, regenerated by a background job. It would keep history perfectly stable across edits, but reintroduces the exact drift risk (stream and guide reading from state that can disagree) that the pure-function design exists to eliminate, plus the operational cost of a regeneration job — at odds with the single-binary-simplicity design lens.
